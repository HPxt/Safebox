SafeBox Security Program

O programa hoje combina proteção do vault no dispositivo, identidade ancorada no Supabase Auth, backend focado em validação e operações sensíveis, e hardening operacional sem reset, sem migration destrutiva e sem apagar os dados existentes.

O projeto saiu de um estado com segredos no histórico, 2FA frágil, import/export inconsistente e boundaries misturados entre frontend, backend e Supabase para uma base mais endurecida. A revisão consolidou hardening de autenticação, sessão, redaction, outbound HTTP, import/export, vault snapshot, settings e isolamento operacional entre API e trilhas auxiliares.

Grafo de confiança (rede)

Visão simplificada de quem fala com quem, sobre qual canal e o que atravessa cada hop. O cofre sensível permanece como ciphertext fora do processo de derivação no servidor.

Topologia

Azul: tráfego do browser para Auth (sessão) e para a API de dados do projeto (PostgREST / SDK) com JWT — é assim que o cofre cifrado e os metadados de KDF sobem e descem. Verde-água: tráfego do browser para o backend SafeBox (ex.: 2FA e rotas que não devem ficar só no cliente). Violeta: tráfego servidor → Postgres via cliente Supabase (persistência, leituras privilegiadas, jobs). Âmbar tracejado: camada conceptual de caminhos ainda privilegiados ou legados (service_role residual) — mesmo destino, risco a reduzir. As respostas HTTP/WSS seguem as mesmas linhas no sentido inverso (omitidas para legibilidade).

Criptografia do cofre (KDF + AES-GCM)

O que o código faz hoje no cliente: derivação com salt próprio, chave só em memória e cofre em vault-snapshot-v2 com nonce por gravação.

Cliente

Salt: 32 bytes aleatórios (crypto.getRandomValues), codificados em Base64, guardados em users.kdf_salt junto com kdf_params (memória Argon2, iterações, paralelismo, tamanho da saída). Não vai para o banco: a senha mestra em texto claro nem a chave AES exportada de rotina — apenas metadados de KDF e um key_hash (SHA-256 sobre a chave derivada) para verificação futura.

1 · PBKDF2100k iterações, SHA-256, primeiros 16 bytes do salt
2 · Argon2idsalt completo, memória e iterações da config LOW
3 · ChaveCryptoKey AES-GCM 256 bits
4 · Cofrenonce 12 B, tag GCM 16 B, payload JSON cifrado
Por que salt + KDF lentos
O salt impede rainbow tables entre utilizadores. Argon2id acrescenta custo de memória e CPU para ataques offline contra cópias do banco. A derivação corre só no cliente; quem obtém apenas o ciphertext ainda precisa da senha mestra.
Exportação / backup
O formato encriptado de exportação pode usar dois salts e uma segunda derivação encadeada antes do AES-GCM, com hash de integridade opcional — reforço extra quando o ficheiro sai do ecossistema Supabase.

Duas senhas, dois papéis

Separar mentalmente a senha da conta (Supabase Auth) da senha mestra do cofre evita confusão sobre o que o servidor pode ver.

Identidade vs cofre

Senha de login Supabase Auth

  • Autentica a conta e emite o JWT de sessão.
  • O hashing segue o modelo do Supabase (não é o mesmo pipeline Argon2 do cofre).
  • O backend SafeBox confia no token validado, não na senha de login em si.

Senha mestra Zero-knowledge do cofre

  • Nunca é persistida; só entra na RAM do browser para derivar a chave.
  • O que fica na tabela users é kdf_salt, kdf_params e key_hash — não a senha.
  • A chave derivada pode ficar em memória com expiração por inatividade; não é estratégia de armazenamento em localStorage.

Boundary do vault

O que atravessa a rede é ciphertext + metadados criptográficos; credenciais em claro ficam atrás do boundary do processo do browser.

Confidencialidade

O serviço de credenciais no cliente descriptografa o envelope (encrypted + nonce), valida o formato e só então materializa a lista na UI. Conflitos de versão no servidor são tratados com controlo otimista para evitar sobrescritas silenciosas entre sessões.

API hardening e segurança de código

Resumo do que o servidor Express aplica por omissão, alinhado ao código em produção e ao quality gate.

Backend

Helmet + CSP

default-src 'self', scripts restritos, ligações Supabase em connect-src, HSTS com preload, frame bloqueado.

CORS fechado

Origem validada contra lista configurada; pedidos fora da allowlist são recusados com registo mínimo.

Rate limiting

Middleware global condicionado a feature flag; reduz abuso de scraping e força bruta na superfície HTTP.

Corpo e parsing

JSON e urlencoded limitados a 2 MB; sanitização de entrada após o parse para reduzir payloads anómalos.

Erros e logs

Respostas ao cliente normalizadas; objectos de contexto passam por redacção antes de logging.

2FA no servidor

Segredos TOTP tratados com AES-256-GCM e chave derivada de segredo de ambiente — fora do caminho do cofre zero-knowledge.

Código e CI
Lint, type-check, testes e build obrigatórios no workflow de quality gate. A API principal permanece separada da árvore auxiliar de IA no processo de verificação, reduzindo risco de dependências não auditadas no mesmo pacote.
Cliente complementar
Rate limiting progressivo local após falhas de derivação, comparação de chaves em tempo constante na verificação da senha mestra, e validação forte de política de senha antes de aceitar o primeiro unlock.

Alterações Técnicas Realizadas

Resumo dos blocos de mudança aplicados para sair do estado inicial mais arriscado sem operações destrutivas no banco.

Backend
Camada compartilhada para validação, autorização, redaction, tratamento de erro, auditoria privilegiada e outbound HTTP. SQL bruto desabilitado. Sessões revogáveis, auth legado desabilitado por padrão, jobs isolados por feature flag e logs operacionais sanitizados.
Frontend
Snapshot atual do cofre, compatibilidade de settings em schema legado, import/export/backup corretos, rotação segura da senha-mestra e limpeza ampla de logs sensíveis em auth, vault, preferências e UX.
Arquitetura
Separação mais clara entre frontend, Supabase Auth, backend e dados. Rotas de perfil/logout/refresco convergiram para o boundary do Supabase e o auth legado do backend ficou desabilitado por padrão, com a API principal isolada da trilha de IA no build e no quality gate.

Risco Residual

O que ainda exige decisão de arquitetura ou uma nova rodada específica de endurecimento.

Risco Residual Alto

  • Segredos historicamente expostos continuam sendo, na prática, potencialmente comprometidos.
  • Ainda existe superfície residual apoiada em service_role e caminhos legados de auth no backend.

Risco Residual Médio

  • 2FA depende do backend publicado corretamente, o que é desejável para segurança, mas exige disponibilidade operacional.
  • A trilha src/ai foi isolada do gate principal e precisa de uma rodada própria de saneamento.
  • Deploy estático ainda depende de compatibilidade/fallback em alguns fluxos do frontend.
Este relatório reflete uma trilha de endurecimento executada sem reset, sem migration destrutiva e sem apagar o banco. A leitura correta do estado atual é: a base está muito mais segura do que estava, mas ainda existe trabalho arquitetural para completar a convergência entre frontend, Supabase Auth, backend SafeBox e operações privilegiadas.
