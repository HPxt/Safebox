Resumo Executivo

O projeto evoluiu de um estado com exposicao de segredos, 2FA fragil, import/export inconsistente e isolamento multi-tenant dependente de filtros manuais para uma base mais endurecida. As correcoes mais relevantes desta rodada foram: redaction e tratamento de erros no backend, sessao revogavel, SQL bruto desabilitado, cliente HTTP com allowlist, import/export baseado no snapshot atual do cofre e migracao do 2FA para verificacao server-side com segredo criptografado. Nesta etapa, o vault passou a trafegar como snapshot cifrado do frontend para o backend, as rotas de vault e settings passaram a usar cliente user-scoped com RLS, a camada de dominio do vault foi extraida e os scripts de API, IA e manutencao foram separados.

Boundaries de Auth e Confianca

O desenho abaixo resume onde cada boundary de autenticacao comeca e termina, e qual risco existe quando esse limite fica misturado.

Navegador / Cofre Local

O frontend manipula o snapshot do cofre, a chave local da sessao do vault e a serializacao do ciphertext. Aqui vivem a UX, o unlock da senha mestre e a montagem do envelope criptografado.

Boundary: dispositivo do usuario

Supabase Auth

Identidade primaria do usuario no estado atual do app. O token do Supabase agora tambem serve como identidade para os endpoints server-side de 2FA.

Boundary: identidade

Backend SafeBox

Responsavel por auth, sessao, audit logs, validacao, hardening, settings, restore/backup do vault e 2FA criptografado server-side, sem receber a senha mestra em claro.

Boundary: autorizacao e seguranca

Supabase Data / Service Role

Camada de dados e operacoes privilegiadas. O risco caiu porque vault e settings migraram para cliente user-scoped com RLS, mas ainda existem superficies legadas que dependem de service_role.

Boundary: dado multi-tenant
Leitura arquitetural: o boundary de identidade ficou mais claro e o boundary do vault agora esta melhor isolado. O passo arquitetural restante mais importante e terminar a migracao das superficies legadas para cliente user-scoped por padrao.

Alteracoes Tecnicas Realizadas

Backend

  • Camada compartilhada de seguranca para validacao, autorizacao, redaction, tratamento de erro e outbound HTTP.
  • Sessao JWT vinculada a user_sessions, com verificacao de token, refresh e revoke.
  • 2FA server-side com segredo criptografado em users.two_factor_secret.
  • Vault e settings migrados para cliente user-scoped com RLS e camada de dominio VaultSnapshotService.
  • Middleware adicional para autenticar token do Supabase quando o fluxo precisar identidade client-side segura.
  • Entrypoints separados para API, worker de IA e job de manutencao.
  • SQL bruto desabilitado.

Frontend

  • Vault snapshot trafegando como ciphertext para o backend, sem enviar a senha mestra em claro.
  • Import/export/backup migrados para o snapshot atual do cofre.
  • Merge de importacao com fingerprint para evitar duplicatas de backups antigos.
  • Backup criptografado do SafeBox com envelope legivel e validacao de integridade.
  • Preferencias migradas para a API backend, alinhando auth/sessao/audit numa unica fronteira.
  • 2FA ajustado para setup, verificacao e recovery por codigo de backup via backend.
  • Logs sensiveis de debug removidos dos fluxos de login, auth context e leitura do vault.

Risco Residual

Risco Residual Alto

  • As credenciais previamente expostas no historico antigo devem continuar sendo tratadas como comprometidas; nesta rodada voce optou por nao rotaciona-las por ser um projeto de testes.
  • O backend ainda possui superficies legadas com service_role, o que nao e o desenho ideal para multi-tenant.

Risco Residual Medio

  • O 2FA agora esta mais seguro, mas passa a depender da disponibilidade do backend para verificacao.
  • A separacao operacional entre API, IA e jobs ja existe em scripts e entrypoints, mas ainda pode evoluir para deploys distintos no futuro.
  • O frontend ainda possui warnings antigos de qualidade e acessibilidade fora do escopo desta rodada.
